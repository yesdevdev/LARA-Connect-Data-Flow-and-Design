§ 01

Product Overview

LARA Connect is the collaboration layer of the LARA suite — a unified project workspace where architecture, engineering and construction teams run their projects day-to-day.

What it doesBrings chat, tasks, tickets, files, meetings, notes and project intelligence into a single per-project workspace, scoped by Service Arm (Architecture, MEP, Structural, etc.).
Main purposeEliminate context-switching between Slack/Jira/Drive/Zoom by giving every project a single command center linked to the broader LARA module ecosystem (Pulse, Markup, Resolve, Pivot, Lens, Meet).
Target usersProject Managers, Architects, MEP/Structural engineers, BIM coordinators, QS, Interior teams, and clients invited to specific projects.
Core value propositionOne channel per project arm, every artefact in the same place, an AI assistant that already knows the project's tasks/tickets/notes, and one-click deep-link to the sibling LARA modules.

Core Features Breakdown

Each feature surface below is a tab inside a channel. Click any card to expand its specification — purpose, inputs, outputs, dependencies, and edge cases.

2.1 Channels workspace spine
+
PurposePersistent room scoped to a Project × Service Arm. Hosts all sub-tabs.
User actionsOpen channel, switch tabs, open threads, archive, leave/join.
System actionsResolve membership, last-activity sort, unread counts, tab visibility by kind.
InputschannelId, kind, projectId, serviceArmId, membership list.
OutputsChannelBrief + members + dmCapability for the header/strip.
DependenciesProjects, Service Arms, Users, Auth.
PermissionsACTIVE members read/write; non-members 404.
Edge casesDM/THREAD channels are chat-only (no tabs). PRIVATE_THREAD includes a reduced tab set.
Scalability notesMove tab-allowlist from client to server policy; cache ChannelBrief per session.
2.2 Chat Tab
+
  • Purpose: Free-form messaging with message types (POST, UPDATE, DECISION, BLOCKER, NOTE, QUESTION, REMINDER, SYSTEM), threads, reactions, pins, convert-to-task/ticket.
  • Inputs: message body, mentions, attachments, parent ID for threads.
  • Outputs: MessageDTO[] for the timeline, MessageThreadBrief for the thread dropdown.
  • Edge cases: edited / deleted messages, mention completion against ACTIVE members only.
  • Future: server-side full-text search; live presence indicators via WebSocket instead of poll.
2.3 Modules / Tasks sibling: Pulse
+
  • Purpose: Per-project task board (List / Board / Calendar views, group by status/priority/assignee/dueBucket, custom fields, renameable labels).
  • Inputs: TaskDTO (title, status, priority, assignees[], due/start, estimatedHours, customFields).
  • Outputs: filtered/grouped views, status timeline, per-module thread channels.
  • Dependencies: Modules config (ModulesConfig), channel members, project.
  • Permissions: project members can create/edit; archived projects read-only.
  • Edge cases: multi-assignee but assignee mirror kept for legacy views.
2.4 Files / Markup sibling: Markup
+
  • Purpose: Per-channel file shelf with previews, versioned uploads.
  • Inputs: FileDTO (filename, mimeType, byteSize, version, uploadedBy).
  • Outputs: gallery + version timeline; deep-link out to Markup module for annotation.
  • Edge cases: DM channels block uploads by policy.
2.5 Tickets / Resolve sibling: Resolve
+
  • Purpose: Structured issue tracker — BUG | RFI | COORDINATION | CHANGE_REQUEST | CLARIFICATION × status × priority.
  • Inputs: TicketDTO (code, kind, status, priority, reporter, assignee).
  • Outputs: ticket list + per-ticket workflow.
  • Edge cases: ticket code auto-generated per project namespace.
2.6 Team / Pivot sibling: Pivot
+
  • Purpose: Member roster with skills, presence, working hours, scheduled statuses.
  • Inputs: UserBrief / UserDetail, project membership state (ACTIVE / etc.).
  • Outputs: searchable roster + hover-card across the app.
2.7 Insights / Lens sibling: Lens
+
  • Purpose: Per-channel KPI snapshot for the last N days (default 14).
  • Output shape: ChannelInsights { messageCount, activeMemberCount, tasksOpen/Done, ticketsOpen/Resolved, filesCount, pinsCount, messagesPerDay[], topAuthors[] }.
2.8 Meetings / Meet sibling: Meet
+
  • Purpose: Scheduled meetings, call history, paste-link import (Zoom/Meet/Teams), MOM note linkage. Upcoming meetings surface in the channel and in the global Calendar.
  • Stores: call-log-store.ts (per-channel), meetings-store.ts (global, filtered by channel/user).
  • Edge cases: missed-call badge in channel header bell, "Join" affordance ≤ 5 min before start.
2.9 Notes internal — no sibling module
+
  • Purpose: Per-channel notebook (sections × pages × sub-pages). Text pages back BlockNote; whiteboard is a P1 stub.
  • Special: "Meeting" sections auto-link to MOM pages created from calls.
2.10 Calendar global surface
+
  • Purpose: One unified upcoming-meetings view across all projects the user is in. Hosts the Schedule Meeting dialog with a Project picker (auto-filled when launched from a channel).
  • Source: same meetings-store.ts consumed by per-channel Meet tabs.
2.11 AI Tab new · per channel
+
PurposePM-facing project assistant grounded in the channel's tasks, tickets, files, notebook, members, recent messages, insights.
User actionsType / pick a suggested prompt, clear conversation.
System actionsAggregate ProjectAiContext, route the prompt through a heuristic table, simulate latency, append assistant reply.
InputsPrompt string + live data from 6 react-query keys.
OutputsAiChatMessage appended to per-channel localStorage thread.
Dependenciesai-engine.ts, ai-chat-store.ts, all channel data queries.
PermissionsVisible only on PROJECT_SERVICE_ARM channels.
Edge casesFalls back to summary when no route matches; thread cleared without touching project data.
FutureSwap heuristic router for real LLM (single-file change in ai-engine.ts); add embeddings over notebook pages and message history.
2.12 Broadcast
+
  • Purpose: Org-wide / multi-channel announcements with delivery to selected channel set.
  • Edge cases: high-priority broadcasts pin to the top of the recipient channels.
2.13 My Tasks / Reminders / Dashboard
+
  • Personal cross-project surfaces aggregating data from all channels the user is ACTIVE on.

§ 09

AI Features

9.1Context flow (today)

AiTab aggregates the 6 live react-queries into a ProjectAiContext:

ProjectAiContext {
  channel, members, insights,
  tasks, tickets, files, notebook,
  recentMessages
}

This blob is handed to runAiQuery(prompt, ctx). A regex route table maps the prompt to a topical builder: summary · blockers · overdue · risks · who-needs-help · upcoming · people · notes. Each builder consumes only the slices it needs and emits a Markdown-ish string.

9.2Memory handling

  • Per-channel thread is local-only (localStorage:lara-connect:ai-chat:<channelId>).
  • No cross-channel memory. No PII leaves the browser.
  • "Clear" wipes the thread without touching project data.

9.3Production AI pipeline (target)

prompt + (channelId, projectId)
   │
   ▼
Context Builder service
   ├─ Pulls live records (tasks, tickets, members)
   ├─ Retrieves top-k vectors from pgvector
   │      (notebook chunks + recent messages, embedded nightly)
   └─ Trims to model token budget
   │
   ▼
LLM call (Claude) with tool-use:
   ├─ get_tasks(filter)        ─┐
   ├─ get_tickets(filter)       ├─ data tools
   ├─ get_messages(query)       │
   ├─ get_notebook_page(id)    ─┘
   ├─ create_task(...)          ─┐
   ├─ post_message(...)          ├─ action tools (require confirm)
   └─ schedule_meeting(...)     ─┘
   │
   ▼
Reply (with citations) → streamed to UI

9.4Security & privacy

  • Tenant isolation in retrieval — every embedding row has projectId and is filtered before the LLM ever sees it.
  • Action tools require explicit user confirmation in chat before execution (no auto-write).
  • Audit log entry per AI tool call (caller, tool, args, project).
  • Opt-out toggle per project for data use beyond the live request.

§ 14

Final Summary

LARA Connect is a well-shaped prototype of a project collaboration platform purpose-built for AEC workflows. The information model (Project → Service Arm → Channel → Tabs) is coherent, the per-channel tab pattern keeps cognitive load low, and the recent additions — global Calendar, AI per channel — extend it without breaking that mental model.

Strengths

  • Clean separation between feature surfaces (src/features/*) and shared primitives (src/lib, src/components).
  • Consistent state pattern (react-query for server state, zustand for auth, localStorage observer stores for client-only domains).
  • Deep links into sibling LARA modules give Connect a genuine "hub" role.
  • New AI tab is grounded in real channel data, persists locally, and is architected so the heuristic engine can be swapped for an LLM in one file.

Weaknesses

  • No real backend yet — api.ts is the only contract.
  • Permissions are still descriptive; server-enforced RBAC is the missing pillar.
  • No realtime layer; live presence and message arrival are mocked.
  • AI is heuristic; no embeddings, no citations.
